# Workgraph v0.6.2 preview

Workgraph 0.6.2 adds offline capability discovery so an agent can describe an
outcome, find a small set of relevant operations and read the exact contract
before acting. The portable skill and packaged references now guide that path
without requiring a full API catalog or schema dump.

This patch keeps application API **0.6**, affected stored roots **5** and saved
upload plan **2**. Existing 0.6.0 and 0.6.1 data, contexts, exact retry journals
and upload plans remain usable without a reset or migration. Upgrade the client
and daemon together, restart the daemon gracefully, and replace the complete
skill folder and companion helpers. See [upgrade steps](#upgrade-from-060-or-061).

These notes describe behavior and upgrade requirements. The matching release
qualification records identify the final commit, source identity, artifact hashes
and observed source, installed-package and platform checks. Prior-release records
and these instructions do not qualify a new executable. See
[validation](../validation.md) for the verification workflow and limits.

## Find an operation from an intended outcome

```sh
workgraph capabilities
workgraph discover 'ask another agent a question'
workgraph discover 'write multiple tasks atomically' --limit 3
workgraph discover 'import a conversation transcript' --kind workflow
workgraph help request
workgraph help workflow.ask_question
workgraph help request.ask
```

`capabilities` introduces **eight feature categories**. Their decision cards cover
**52 API groups**. The discovery catalog describes all **267 daemon methods**,
**22 local helpers** and **nine workflow recipes**. Entries distinguish these kinds
and include a purpose, use condition, effect and next help command. The categories
are planning, worker coordination, communication, durable context, recovery,
verification, observation and local administration.

`discover` returns at most **five entries by default**. Use `--limit 1..20`,
`--capability ID` and `--kind method|helper|workflow` to narrow the response. Text
is the default; `--output json` reports structured results, decimal-string
matched/returned counts and `has_more`. Queries are bounded to **1024 UTF-8
bytes**. `discover --catalog` is an explicit complete metadata export without
request/result schemas; ordinary discovery does not dump the catalog.

All of these commands read metadata compiled into the executable. They work
without a daemon, socket or context file and do not create workspace records or
execute suggested operations. `search.query` continues to search recorded work;
`history.search` continues to search imported conversation history. Neither is
an API discovery command. Discovery categories are also separate from a registered
run's cooperative eligibility capabilities.

## Read detail progressively

`capabilities ID` explains one feature area. `help FAMILY` gives a group decision
card with its purpose, use condition, distinction from adjacent concepts and
starting operations. `help workflow.ID` provides an ordered recipe; `help METHOD`
continues to provide exact inputs, examples and prerequisites. Curated method
summaries and related-operation links connect those layers. `fields METHOD` and
`schema METHOD` retain their deeper machine-readable contracts.

The nine recipes cover planning, working a ticket, asking a question, sharing
context, observing changes, recovering work, verifying outputs, backup/restore and
importing conversation history. Recipes describe required checks and ownership
boundaries; the harness still performs external actions. The evidence group card
also distinguishes the daemon's evidence read from local capture and publication
helpers.

The copied skill now introduces concise discovery before detailed guide routing.
Generated capability, group and workflow references accompany the generated API
reference. Both inventories derive from the executable catalog; coverage, links,
reference drift and copied-skill checks keep them aligned with the shipped CLI.
No parallel request schema or new daemon API method was added.

See the [discovery contract and maintenance guide](../agent-discovery.md) and
[portable discovery index](../../skills/workgraph/references/discovery/index.md).

## Agent exercises and refinements

Two fresh GPT-6.1 Sol agents at high reasoning used a copied executable, the
portable skill and isolated workspaces. They received desired outcomes and
connection values, with no method names or repository source, and were instructed
not to load a full catalog or schema. Both completed their assigned outcomes:

- One planned and delivered documentation through dependent tickets, scoped facts,
  a versioned checklist, progress and handoffs. It asked a separate maintainer for
  a decision, retrieved the exact answer, explicitly acknowledged notifications
  and completed the work with readback.
- One registered a run and attempt, acquired and released a logical reservation,
  imported two synthetic messages, searched and retrieved the exact 104-byte
  source payload with a matching hash, reconstructed context and produced a
  readable workspace export.

Observed friction and independent reviews led to concise discovery being moved
ahead of long guides, the transcript-import recipe, capability-name help fallbacks,
related-method navigation for path operations and explicit handoff-coverage
guidance. The transcript converter accepts selected Claude records; the recipe
does not promise arbitrary JSONL compatibility.

These are qualitative workflow exercises, **not a statistical reliability
benchmark or token-efficiency comparison**. The export was integrity-verified;
canonical state was not replay-validated and no restore was performed. Reservations
were cooperative records rather than filesystem enforcement. The exercises did
not run production builds, deploy services or verify synthetic transcript claims.
See [observed exercises and limits](../agent-discovery.md#observed-agent-exercises).

## Install

Use the matching [AlmaLinux/WSL quick start](../wsl-quickstart.md),
[macOS guide](../macos-install.md) or
[source build](../../README.md#build-the-current-checkout-from-source).
Native packages are AlmaLinux 10 x86_64 RPM/tar and macOS ARM64 tar; source and
standalone skill archives accompany them. Verify the selected asset filename
against the release's `SHA256SUMS` before extracting or installing it.
`workgraph --version` must print `0.6.2`; `initialize` must report package `0.6.2`,
application API `0.6` and registry format `5`.

Install the complete [agent skill](../agent-skill.md) and companion files together.
Do not merge old generated references into the new folder. Native executables
need no OCaml/opam installation. WGX and example/qualification helpers retain their
separately documented Bash, jq, Python and Git requirements.

## Upgrade from 0.6.0 or 0.6.1

1. Locate the actual executable, daemon socket, registry/workspace roots, contexts,
   exact request journals, saved transfer plans and launchers. Preserve matching
   previous-release archives before replacing installed files.
2. Drain active work and shut down the daemon gracefully. Retain uncertain writes
   and their exact saved requests; changing a mutation identity cannot establish
   the original outcome. Back up the complete stopped roots, contexts and journals.
3. Install the verified 0.6.2 executable and retarget launchers deliberately. Use
   the same 0.6.2 build for client and daemon. Restart against the existing 0.6
   roots and socket; retain existing contexts and request directories.
   **No fresh roots, journal reset or format-marker edits are required.**
4. Replace the entire skill folder and WGX companion helpers with matching 0.6.2
   copies, preserving local customizations separately. Discovery references and
   curated summaries must match the executable; keep companion scripts together.
5. Check `--version`, offline `capabilities` and `discover`, `initialize` and a read
   through the intended context. Preserve exact retry identities when resolving
   saved uncertain requests. Resume work after confirming the endpoint and roots.

When upgrading directly from 0.6.0, also apply the
[0.6.1 shell and continuation requirements](v0.6.1.md#upgrade-from-060): JSON-mode
errors are structured envelopes on stdout with a nonzero exit status, and bounded
nested collections expose independent exact continuations. Check success before
consuming a grant and follow explicit captures before treating a context as complete.

Package version is distinct from API and storage-format identifiers. This patch
keeps API `0.6`, roots/exports `5`, upload plans `2`, and independent planning/history
heads, history batches and heartbeat caches `1`. It adds no compatibility reader
for another schema and makes no general downgrade promise.

## Upgrade from 0.5 or an older preview

Follow the [preservation-first 0.6 upgrade procedure](v0.6.0.md#upgrade-from-05-or-an-older-preview).
Preserve the old binary and data, resolve or retain exact uncertainty with that
reader, export and verify needed material, then use fresh 0.6 roots, socket,
contexts and request journals. Old exports are not a cross-format restore path.
The absence of a storage change in 0.6.2 does not make 0.5 data compatible.
No deletion is required; never broadly remove managed roots, locks or sockets to
force an upgrade.

## Qualification and limits

Release qualification must bind this exact source and all published artifacts to
the observed full `@fmt @runtest @install` gate, generated-reference checks,
installed-runtime checks and archive hashes. Consult the accompanying matching
qualification JSON and evidence archives for results actually observed. Agent
exercises supplement those checks; they do not qualify a platform or artifact.

AlmaLinux container checks cover its userspace on the host kernel; they do not
qualify an actual Windows/WSL kernel or SELinux policy. macOS deployment minimum,
tested OS, Developer ID signing, notarization and downloaded Gatekeeper launch
require explicit matching evidence. Neither prior-release qualification nor a
successful local build establishes those claims for this release.

Discovery uses deterministic English keyword matching, curated terms, basic word
normalization, exact-name priority and weighted multiword coverage. It is not
semantic search. No result means no lexical match under the selected filters,
not proof that a feature is absent. Broaden a query, remove filters or browse a
category. A matching operation still requires its exact preconditions and the
user's authorized scope. Larger runtime context responses can remain verbose;
this release improves offline navigation rather than their payload shape.

Workgraph remains a lightweight local cooperative state service. This release
changes no storage formats, authentication model or daemon operation modes. It
adds no model runtime, MCP server, distributed coordination, automatic ownership
takeover, history pruning or garbage collection. The harness continues to own
processes, prompts, external side effects and safe source isolation.
