# Workgraph 0.8.0 — optional local UI

Workgraph now has a browser interface for people working alongside agents. The
optional `workgraph-ui` executable serves its own embedded assets and connects to
a matching local Workgraph daemon. The CLI remains independently installable.
Installed operation needs neither Node.js nor opam, a hosted service, or model credentials.

## What you can do

- **Overview:** follow ready, active, blocked and completed work, outstanding
  questions, project progress and recent activity. Colored status indicators and
  participant avatars make the state easier to scan.
- **Work:** browse a board or grouped list, search and filter by known participants,
  create and edit tickets, change priority, read and add comments, and inspect
  dependencies, completion requirements and who can take the work. Ticket
  conversations use readable message threads and open by default.
- **Workflow:** trace a ticket's connected dependencies without covering the graph,
  zoom and fit the graph, inspect relationships, and build reusable templates and
  drafts. Guided review explains what a proposed batch will change before applying it.
- **Discussions:** read boards and threads, send messages, ask accountable questions,
  answer requests, check received messages, and configure teams and subscriptions.
  Workspace-aware pickers help find actors, tickets and destinations.
- **Participants:** inspect people, agents, runs and attempts, allocation rules,
  reservations, outside conditions and recovery records. Workgraph records these;
  it does not launch agent workers or enforce a process sandbox.
- **History:** browse and search imported sessions, read chronological conversations,
  combine recognized tool calls with their results, and inspect source JSON when
  needed. Specialized adapters cover Codex and Claude Code JSONL and supported
  OpenAI/Anthropic API shapes. Load more messages or the full session, and follow
  new entries at the latest end. Unknown formats retain a general source view.
- **Usage:** inspect reported input/output tokens, other metrics and reported cost.
  Shared run usage is counted once. Session totals include attributable runs and
  identify shared usage; they do not invent a per-session split. These are recorded
  metrics, not an independently verified invoice or automatic model-price lookup.
- **Resources and facts:** browse versioned files and small shared facts, render
  Markdown, highlighted code, lossless JSON and supported static images, compare
  versions and manage stored content.
- **Saved views and activity:** create reusable views of recorded data and inspect
  changes. Guided editors explain fields and preserve unfinished drafts.
- **Connections and scope:** connect to multiple local daemons, explicitly start
  one, create or select workspaces, pin projects for quick switching, and retain
  the selected actor across refreshes. Observer mode remains available. A write
  requiring an actor opens the actor chooser.

The UI uses a consistent dark/light design with readable typography, rounded
panels, colored icons, helpful empty states and contextual explanations. Background
refreshes preserve selections, expanded details and reading position instead of
replacing the page with loading messages. See the [UI guide](../ui/README.md).

## Changes are reviewed and recoverable

Writes use the same daemon rules as the CLI. Review a change, then explicitly apply
it. Saved drafts retain their original connection, workspace, actor and guards;
changing the current selection does not silently retarget them. An uncertain write
retains its exact request identity for receipt lookup or an explicit identical
retry. A browser disconnect does not establish whether a write succeeded.

Actor names provide cooperative attribution, not authentication. The companion is
loopback-only and does not add a model runtime, MCP server or remote multi-user
service. Browser content is passive: imported Markdown and saved views cannot run
scripts or automatically load external images.

## Core fixes included

- Transaction preflight reports the **actual expanded operation count**, including
  template expansion, so a reviewed plan can be compared with the 128-operation
  limit correctly.
- Subscription filters accept all nine supported communication kinds.
- Reservation-wait recovery validates a recovered acquisition against its original
  method's response, preserving exact retry semantics.
- Resource upload publication and follow-up ticket linking share validation of the
  resource, version, actor, filename, media type, size and digest.
- Local daemon startup has a reusable qualified entry point. The UI checks exact
  package compatibility before daemon work and does not treat a startup handshake
  as proof it owns the daemon process.

## Downloads and installation

The [release assets](https://github.com/dakotamurphyucf/workgraph/releases/tag/v0.8.0)
include core-only packages, the full source and agent skill, and optional UI packages:

| Package | What it contains |
| --- | --- |
| `workgraph-ui-0.8.0-macos-arm64.tar.gz` | Apple Silicon native UI, paired daemon and offline documentation |
| `workgraph-ui-0.8.0-almalinux-10-x86_64.tar.gz` | AlmaLinux 10 AMD64 native UI, paired daemon and offline documentation |
| `workgraph-ui-0.8.0-1.el10.x86_64.rpm` | UI executable and documentation; requires the exact matching core RPM |

Verify the selected asset against `SHA256SUMS` before extracting or installing it.
The [UI installation guide](../ui/installation.md#install-a-release) includes
commands. [AlmaLinux/WSL quickstart](../wsl-quickstart.md) covers the core setup.
Start `workgraph-ui --state-root "$HOME/.local/state/workgraph-ui"`; add `--no-open`
when opening the printed URL yourself, and `--port 8765` for a stable local port.
The interface lets you attach to an existing daemon or deliberately start one.

## Upgrade from 0.7.0

No workspace reset or data migration is required from **0.7.0**. Stop or hand off
your old daemon deliberately, install the matching **0.8.0 core and UI** together,
and restart using your existing registry and workspace locations. Keep all private
data outside installation directories. Resolve uncertain saved operations with
their original executable before changing versions; preserve their journals.
Update agents' bundled skill alongside their executable.

Application API **0.7**, workspace/export format **6**, history batch format **2**,
saved upload plan **2**, and registry/planning transaction/event format **5** are
unchanged. The API number alone does not establish UI compatibility: the companion
requires its exact package version.

For **0.6.2**, use the explicit [offline migration helper](../migration.md), which
writes a fresh root while preserving the source. Other prototype formats are not
supported. Startup does not silently convert data. Removing the UI leaves workspace
roots, companion settings and request journals alone; see [removal guidance](../ui/packages.md).

## Qualification and limits

Release qualification uses the actual packaged executable pair, source and asset
manifests, checksums, native inspection and installed-runtime checks. The core gate
includes formatting, unit and real daemon/socket tests. The frontend gate includes
lint, strict type checks, formatting and 1,303 unit tests; focused browser checks
exercise real daemon interactions. The full visual walkthrough was approved by
the user. Qualification reports are published with the artifacts.

- macOS targets **ARM64**. Builds are not Developer ID signed or notarized;
  downloaded Gatekeeper behavior and native Safari are not qualified.
- AlmaLinux targets **10 x86_64**, requiring an x86-64-v3-capable CPU. Runtime
  qualification is separate from a Windows browser connecting through WSL.
- **Windows-to-WSL browser qualification is deferred** to post-release user testing.
  Users configure their own forwarding while retaining the printed URL's host and
  port. Workgraph does not configure Windows networking or offer LAN binding.
- Unknown, partial or oversized content remains identified as such; adapters do not
  promise to understand every future provider schema. History is general recorded
  data, not necessarily an agent conversation.
- Recorded ownership, eligibility and cost do not prove external process liveness,
  enforce an agent sandbox or establish billing accuracy.
