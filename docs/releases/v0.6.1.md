# Workgraph v0.6.1 preview

Workgraph 0.6.1 fixes captured reads, CLI error handling and reservation convenience,
and raises the bounded atomic transaction limit. It keeps application API **0.6**,
affected stored roots **5** and saved upload plan **2**. Existing 0.6.0 data,
contexts, exact retry journals and upload plans remain usable without a reset or
migration. Upgrade the client and daemon together, restart the daemon, and replace
the complete skill folder and companion helpers.

This document describes behavior and upgrade requirements. The matching release
qualification records identify the final commit, source identity, artifact hashes
and observed source, installed-package and platform checks. Prior-release records
and the instructions here do not qualify a new executable. See
[validation](../validation.md) for the verification workflow and limits.

## Captured reads and continuations

- `ticket.recovery.list` continuations retain the planning workspace capture
  instead of inferring a run-coordination `query_revision` from its request guard.
  `recovery.list` retains its separate run-coordination capture. Both methods are
  exercised through real daemon/socket comparisons, including filtered pages and
  stale guards.
- `ticket.context`, expanded `thread.get` and `request.get` now expose independent
  nested collection continuations in `meta.pagination.sections`. Each section
  identifies its path, completion/stop reason and an exact next or retry request.
  Communication continuations retain both the communication revision and discussion
  serial; planning continuations retain their workspace capture and selectors.
  Fact-key discovery can continue through `fact.keys` with the same ticket scope
  and capture; `response_path` names the collection in that continuation response.
- Clipped text requires a retry at the same position with a larger budget; it does
  not advance beyond omitted content. Missing explicitly requested related-message
  expansion rejects instead of appearing complete. No automatic nested traversal,
  merging or snapshot refresh is performed. Existing flat `--paginate` traversal
  retains its separate behavior.
- Pagination byte accounting is explicit: daemon `meta.budget` describes the
  original page, while `meta.pagination.max_bytes` and `returned_bytes` measure
  only the client-added continuation metadata. The metadata remains capped at
  **64 KiB** independently of the page budget. Oversized continuation metadata
  reports `metadata_limit` instead of clipping an exact request or changing capture.

See [pagination contracts](../../skills/workgraph/references/cli-contract.md#exact-continuation-on-a-single-page)
for the complete request and capture rules.

## Requests and upload discovery

`request.get` includes `data.question`, the question body at its original pinned
comment ID and revision, alongside the pinned answer. Editing the current comment
cannot replace the original question shown by this read. Public decoding validates
that the expanded body matches the pinned reference. Both expansions remain
subject to response budgets; inspect omissions before treating a body as complete.

`upload.status` and `upload.list` are classified as reads. Context defaults still
supply the required staging-owner actor for `upload.status`; `upload.list` receives
only the workspace default so it can discover all staging owners. Listing does
not silently filter by the caller's actor/run context.

## CLI failures and reservation helpers

**JSON-mode failures now produce a JSON-RPC error envelope on stdout and exit
nonzero**, including local argument, context and parameter-file failures. Scripts
that previously expected empty stdout on failure or parsed error prose from stderr
must check the exit status first and read the structured error from stdout.
Saved-request diagnostics remain on stderr. Text and raw-byte output commands keep
errors on stderr so they cannot contaminate their output stream. Exact saved retry
identities and uncertain-write classification are preserved.

For example, save a JSON response only as a grant after the command succeeds:

```sh
"$WG" --context "$CONTEXT" reservation wait --self \
  --json-field requests '[{"reservation_id":"test-db","mode":"exclusive"}]' \
  > "$AGENT_DIR/wait.json" || exit 1
jq -e '.result.data.wait.completed == true' "$AGENT_DIR/wait.json" >/dev/null || exit 1
```

`--self` supplies a missing reservation ownership `target_run_id` from context for
`reservation acquire`, `reservation paths acquire` and their local wait helpers.
Explicit targets win. Invocation `run_id` attribution remains a separate field;
normal ownership checks still require supplied acquisition attribution to match
the ownership run. Selecting a different target does not rewrite inherited
attribution. Missing context/run defaults fail with an actionable diagnostic before
journaling. A context `request_directory` is reused without repeating the flag;
an explicit `--request-directory` overrides it. The directory must already exist.

A wait helper can return JSON describing a conflict or uncertain outcome while
exiting nonzero. Only successful completion and the actual daemon grant permit
protected work. On uncertainty, retry the exact saved request. Neither convenience
option recovers a foreign reservation, renews ownership or promises fairness.

## Larger atomic plans, unchanged byte bounds

Transactions, preflight, durable replay and template expansion now admit at most
**128 expanded atomic operations**, up from 32. A plain template can contain at
most **127 nodes** because final instance registration also consumes one operation;
dependencies and enabled allocation/review policies consume additional operations.
Preview the expanded plan before applying it. Workgraph never splits an oversized
atomic plan automatically.

The **4 MiB wire-frame and authoritative planning-JSON limits remain unchanged**.
Event, workspace-admission and other independent limits still apply, so 128 small
operations do not guarantee that any 128-operation payload fits. Facts remain
bounded to 4096 canonical JSON bytes; larger material belongs in resources.

## Install

Use the matching [AlmaLinux/WSL quick start](../wsl-quickstart.md),
[macOS guide](../macos-install.md) or [source build](../../README.md#build-the-current-checkout-from-source).
Native packages are AlmaLinux 10 x86_64 RPM/tar and macOS ARM64 tar; source and
standalone skill archives accompany them. Verify the selected asset filename
against the release's `SHA256SUMS` before extracting or installing it.
`workgraph --version` must print `0.6.1`; `initialize` must report package `0.6.1`,
application API `0.6` and registry format `5`.

Install the complete [agent skill](../agent-skill.md) and companion files together.
Do not merge old generated references into the new folder. Native executables need
no OCaml/opam installation. WGX and example/qualification helpers retain their
separately documented Bash, jq, Python and Git requirements.

## Upgrade from 0.6.0

1. Locate the actual executable, daemon socket, registry/workspace roots, contexts,
   exact request journals, saved transfer plans and launchers. Preserve the
   matching 0.6.0 archives before replacing installed files.
2. Drain active work and shut down the daemon gracefully. Retain uncertain writes
   and their exact saved requests; changing a mutation identity cannot establish
   the original outcome. Back up the complete stopped roots, contexts and journals.
3. Install the verified 0.6.1 executable and retarget launchers deliberately. Use
   the same 0.6.1 build for client and daemon. Restart the daemon against its
   existing 0.6 roots and socket; retain existing contexts and request directories.
   **No fresh roots, journal reset or format-marker edits are required.**
4. Replace the entire skill folder and WGX companion helpers with their matching
   0.6.1 copies, preserving local customizations separately. Update scripts for
   JSON error envelopes on stdout and check nonzero exit status before parsing a
   success result. Nested-section consumers must follow each explicit continuation
   and its returned capture instead of assuming a bounded context is complete.
5. Check `--version`, `initialize` and a read through the intended context. Preserve
   exact retry identities when resolving saved uncertain requests. Resume work only
   after confirming the intended endpoint and roots.

Package version is distinct from API and storage-format identifiers. This patch
keeps API `0.6`, roots/exports `5`, upload plans `2`, and independent planning/history
heads, history batches and heartbeat caches `1`. It adds no compatibility reader
for another schema and makes no general downgrade promise.

## Upgrade from 0.5 or an older preview

Follow the [preservation-first 0.6 upgrade procedure](v0.6.0.md#upgrade-from-05-or-an-older-preview).
Preserve the old binary and data, resolve or retain exact uncertainty with that
reader, export and verify needed material, then use fresh 0.6 roots, socket,
contexts and request journals. Old exports are not a cross-format restore path.
The absence of a storage change in 0.6.1 does not make 0.5 data compatible.
No deletion is required; never broadly remove managed roots, locks or sockets to
force an upgrade.

## Qualification and limits

Release qualification must bind this exact source and all published artifacts to
the observed full `@fmt @runtest @install` gate, generated-reference checks,
installed-runtime checks and archive hashes. Consult the accompanying matching
qualification JSON and evidence archives for the results actually observed.

AlmaLinux container checks cover its userspace on the host kernel; they do not
qualify an actual Windows/WSL kernel or SELinux policy. macOS deployment minimum,
tested OS, Developer ID signing, notarization and downloaded Gatekeeper launch
require explicit matching evidence. Neither prior-release qualification nor a
successful local build establishes those claims for this release.

Workgraph remains a lightweight local cooperative state service. The harness owns
processes, prompts, external side effects and safe source isolation. This release
does not add distributed coordination, a model runtime, an MCP server, automatic
ownership takeover, history pruning or garbage collection.
