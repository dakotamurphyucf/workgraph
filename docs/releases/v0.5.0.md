# Workgraph v0.5.0 preview

Workgraph 0.5.0 improves cooperative agent workflows from startup and eligible-work
selection through questions, instruction changes, recorded context and completion.
It remains one standalone OCaml/Core/Eio executable: a local state daemon and CLI,
with explicit durable records rather than a model runtime or agent launcher.

**This is a breaking prerelease.** Package **0.5.0** uses application API **0.5**
and affected stored roots **4**. Use the matching executable and bundled guides.
Preserve older binaries, archives, exports and stopped data before changing an
installation. Start 0.5 with fresh registry/workspace roots, socket, contexts and
request journals. There is no automatic migration or older-export restore.

The [release page](https://github.com/dakotamurphyucf/workgraph/releases/tag/v0.5.0)
contains the platform bundles, checksums and separate qualification evidence.
The [README](../../README.md) has the complete tutorial and maintained scripts;
[AGENT_GUIDE.md](../../AGENT_GUIDE.md) is the compact agent entry point.

## Changes delivered

### Safer startup and consistent acquisition

- A lifetime guard serializes ownership of a socket path across registries and
  parent aliases. Crash recovery removes only its exact recorded native socket
  identity after ownership and peer checks. Foreign, live, bound, symlinked,
  replaced or unknown paths refuse. A crash before socket identity publication
  may conservatively require a fresh endpoint. Connection refusal, PID lookup
  and a registry lock alone never authorize cleanup.
- Bootstrap verifies the child's actual readiness handshake and reports bounded
  startup failure, timeout and log diagnostics. Socket existence alone is not
  service readiness; a timeout does not prove a detached child stopped.
- One acquisition assessment aligns direct claims, starts, reassignment, attempt
  admission, automatic allocation, run-aware readiness and durable replay.
  Capability-constrained work requires a compatible registered run. Optional
  `allowed_actor_ids` restrict cooperative scheduling, without authentication.
  A claimed ticket and its nonterminal attempt consume one pool slot together.
- Required automatic path reservations retain exact claim borrowers. Finishing,
  releasing, reassigning or guarded recovery removes only that borrower; the
  final borrower releases the automatic hold. Independent/manual holds survive.
  Receipts expose actual grants, tokens and leases; contention identifies bounded
  conflicting paths/holders. Expiry is not proof a process stopped.
- The opt-in reservation wait helper retries only definite typed contention for
  its original target and guards, within a bounded deadline and attempt count.
  It captures before parking and retains exact journals on uncertainty. It
  promises neither fairness nor permission to recover another holder.

### Idle work and captured attention

- Standalone `ticket.claim_next` distinguishes `selected` from a strictly
  validated nondurable `empty` observation. Empty changes no planning head,
  receipt, attempt, durable bytes or change notification. Inspect `kind` before
  reading `claim.token`; do not treat transport or acknowledgement uncertainty
  as an empty result.
- The same uncommitted empty request identity may reevaluate after work changes.
  Once a selection commits, exact retry returns its immutable original receipt.
  Explicit `transaction.apply` batches remain durable, including empty selection.
- `attention.read` / `attention.wait` combine selected committed activity with
  explicit project, ticket/run, source-kind, fact-prefix and communication
  recipient/consumer filters. Logical notification groups retain every raw ID
  for selective acknowledgement. Captured routing does not move older events
  into a new project after later edits.
- Readiness is a separately paged **current** view, with authoritative run-aware
  eligibility when a run is selected. It is not a history of every transient
  readiness edge. Capture before checking readiness and parking, keep nested
  continuations and advance only consumed cursors. Waits remain outside the
  serialized writer and recheck after relevant wakes. Reads never acknowledge.
- `actor.overview` collects current claims, attempts, named/path reservations,
  incoming/outgoing requests and explicitly selected consumer inbox state in one
  bounded capture. These records do not establish external process liveness.

### Questions, instructions and completion

- Request resolution can pin the exact durable answer comment/version. Later
  comment edits do not change that answer. Receipts distinguish request and
  thread revisions and answer references; plain resolution without a body has
  no answer. Notifications retain exact causal body references.
- Question-created threads close when all their requests are terminal. Ordinary
  threads remain manually closed by default. Ask supports priority/deadline;
  guarded metadata and related/superseding links preserve conversation lineage.
  Superseding a request does not cancel it.
- Immutable ticket instruction amendments carry text or exact resource pins,
  acknowledgement requirements, supersession and withdrawal. Required acceptance
  binds the amendment version and actual actor/run/claim token. Progress and
  lease renewal preserve it; replacement ownership must acknowledge again.
  Completion and replay enforce the gate, including transaction final state.
- `ticket.hierarchy.get` / `put` explicitly opt into ancestor prerequisite
  inheritance. Ownership and parent child-completion gates never inherit.
  Readiness names source blockers; waivers belong to the declaring ticket.
  Canceled children block parent completion unless its local policy permits them.
- `project.readiness` aggregates unfinished, owned and gated work at one capture.
  Guarded `project.finish` records Done plus a structured handoff atomically.
  Equivalent Done transitions enforce the same conditions. Project completion
  does not complete tickets, resolve questions or stop agent processes.

### Discovery, memory and client workflows

- Offline helper, family/action and method help resolve before context or daemon
  I/O. Dotted and documented nested spellings share catalog validation and useful
  suggestions. `--full` and `schema METHOD` expose complete public contracts;
  literal child argv after `--` stays literal.
- Compact ticket/resource briefs improve discovery while full ticket context
  remains bounded and explicit about omissions. Observer contexts may omit write
  attribution; reads remain unfiltered unless selectors are supplied. This is
  convenience, not an enforced read-only security boundary.
- Parameter/text inputs accept one explicit stdin source. Exact bytes and trailing
  newlines are materialized and validated before journaling. Retry rejects new
  input and overrides before reading them. Regular-file inputs do not imply
  support for arbitrary devices or FIFOs.
- Resource updates can omit title to preserve metadata under the exact entity
  revision guard; creation still requires one. Verified large-resource downloads
  avoid manual chunk decoding. Streaming stdout may emit a prefix before a final
  integrity error; use verified spooling for all-or-error emission.
- Bounded typed pagination preserves method, selectors, capture and continuation.
  Incomplete traversal exposes stop/next/retry details and exits unsuccessfully;
  it never silently substitutes the latest capture or invents an empty result.
- `transaction.preflight` runs actual preparation/validation without commits or
  reservations. `transaction.apply` atomically commits up to 32 supported
  operations, with typed creation aliases; external tools and uploads remain
  outside that transaction. Large plans are not silently split into an allegedly
  atomic result.
- Facts support up to eight ANDed scalar-equality JSON-pointer predicates;
  missing differs from null. Up to 32 typed ticket/resource navigation references
  allow reverse discovery through `fact.references`. Those editable links do not
  substitute for immutable evidence pins.
- Recorded resume and activity digest retain selected facts, structured handoffs,
  exact source references, hierarchy/amendment records and explicit coverage and
  byte omissions. They infer no model summary or historical eligibility.
- Immutable usage reports support scoped rollups and up to 16 named nonnegative
  integer measurements with units. Overflow and unallocated run spending stay
  visible. Reported usage is not provider quota enforcement or invented ticket cost.

### Readable evidence, exports and guides

- Bounded decoded execution inspection exposes retained stdout/stderr ranges and
  provenance coverage. Selected sources cover only the declared set; retained
  output cannot recover omitted bytes. Publication retry never reruns execution.
  Publication and ticket linking are separate commits with distinct recovery.
- Stage cleanup is explicit and validates ownership; it does not overwrite or
  prune foreign, live or published evidence. Readable exports retain structured
  handoff fields, attributed decisions and visible history with complete-byte
  references, immutable captures and verified blob inventories.
- The complete README includes eight workflows, atomic result/finish patterns,
  capabilities and pools, explicit source ownership, all `wgx` views, visible
  transcript import, inspection, export/restore and complete maintained scripts.
  Tests compare inline scripts byte for byte with their maintained sources.
  `wgx` uses bounded captured pagination, daemon eligibility and escaped terminal
  text; incomplete panels remain errors. The transcript converter excludes
  private model reasoning and reports unsupported visible content.

## Breaking contracts

| Boundary | 0.5.0 requirement |
| --- | --- |
| Application requests / saved retries | `workgraph_api:"0.5"`; old envelopes are unsupported |
| Registry, workspace descriptor, planning envelope, exports | Current complete format `"4"`; no legacy reader or automatic migration |
| Independent unchanged formats | Planning/history HEAD and history batches, heartbeat cache and upload parameters retain their own `"1"` identifiers |
| Success and retry | Inspect `result.data` / `result.meta`, actual domain IDs and tokens; preserve exact committed receipts |
| Empty automatic allocation | Standalone `empty` is nondurable and may reevaluate; explicit batches remain durable |
| Captured reads | Preserve each method's filter/capture/cursor and nested continuation; stale captures reject |

Public counters remain canonical decimal strings. Unknown/duplicate fields reject;
omission differs from null. Entity/content/history/workspace revisions and cursors
have different meanings. `at_revision` guards a current captured state, not an
arbitrary historical snapshot. See [CLI contracts](../agent/cli-contract.md) and
[format and durability](../compatibility.md) before writing a raw integration.

## Upgrade from 0.4 or an older preview

1. **Inventory and preserve the old runtime first.** Record its executable path,
   version, socket, contexts, registry, every custom workspace root and launchers.
   Retain the matching binary, complete extracted bundle, original native/source
   archives and RPM where applicable. An RPM upgrade replaces `/usr/bin/workgraph`;
   download/preserve the old package and an executable copy before doing that.
   The [v0.4.0 release](https://github.com/dakotamurphyucf/workgraph/releases/tag/v0.4.0)
   remains the matching documentation/package source for 0.4 data.
2. **Preserve recovery identities.** Use the old executable to settle known
   uncertain writes through their exact saved request and receipt procedure, or
   retain those journals for later recovery with that executable. Never submit
   them through 0.5 or reissue an uncertain operation with a new identity.
3. **Export with the old executable and verify.** Follow each actual export job
   to successful completion under a deadline and verify its manifest/inventory.
   Review needed readable artifacts and preserve complete-byte resources/history.
   Export verification checks hashes/inventory; canonical replay happens on
   restore under a matching old executable into fresh old-format roots. An old
   export is a preservation artifact, not a supported import into 0.5.
4. **Stop writers and retain complete data.** Stop old custom launchers, drain
   work and shut down gracefully before copying closed registry/workspace roots.
   Preserve roots, contexts, journals, logs and exports together with the old
   executable. Registry metadata is machine-local and separate from portable
   workspace content. Do not delete locks or socket paths based on failed connects.
5. **Install and verify 0.5.0.** Check the selected asset against `SHA256SUMS`,
   retain its bundled docs/examples and confirm `workgraph --version` prints
   `0.5.0`. Check `type -a workgraph` and clear shell command caches if PATH still
   selects an old manual installation. Use an explicit executable path if needed.
6. **Create a separate 0.5 setup.** Choose fresh private sibling registry/workspace
   roots, a new socket path, new per-agent contexts and new request journals.
   Follow the [bootstrap example](../../README.md#bootstrap-a-private-workspace)
   or [WSL quick start](../wsl-quickstart.md). Do not edit version markers, copy
   old managed JSON into the new tree or restore old exports with 0.5.
7. **Resume deliberately.** Recreate the needed plan in the fresh workspace and
   explicitly transfer selected human-readable material through supported current
   commands if desired, retaining its old provenance. Give each agent its new
   matching guide/context. Keep old data available separately until you decide it
   is no longer needed. Returning to 0.4 means using the preserved 0.4 binary with
   its preserved 0.4 roots; 0.5 roots cannot be opened by the old executable.

Upgrading requires no deletion. A reset is a separate optional destructive action:
stop all owners, verify retained backups and explicitly choose each exact old path
before removing it. Uninstalling a package does not delete custom workspace roots.
There is no automatic schema conversion, merge of disconnected histories or downgrade.

## Qualification and limits

The accepted implementation at `204c6c4fd86e7da784ec4fd2fd93711689024dde`
passed the repository gate and native package checks before the release-facing
documentation update. The [native AlmaLinux run 41696861301](https://github.com/dakotamurphyucf/workgraph/actions/runs/41696861301)
passed independent installed tar and RPM checks in fresh AlmaLinux 10 x86_64
containers without the OCaml toolchain. The macOS ARM64 package passed installed
CLI, Git handoff, export/restore and history recovery on macOS 14.5 with an empty
environment and `/usr/bin:/bin` PATH. Inspected deployment minimum was macOS 14.0,
with only `/usr/lib/libSystem.B.dylib` dynamically linked. Source inventories of
986 files matched between those qualified platform builds.

Those results identify that implementation source; they do not qualify later
changed package bytes. The release's separate platform `qualification.json` and
evidence archives bind the final tested source identity, executable SHA256 and
archive/RPM hashes. Read those records alongside the assets and checksum list.
The embedded `QUALIFICATION.json` is an earlier `inspection-only` record, distinct
from the external final runtime result. Packaging verifies source/native guide
agreement, safe archive members, complete manifests, notice inventories and exact
installed bytes; test expectations and RPM byte checks remain strict.

Actual Windows/WSL kernel execution and SELinux policy are untested. Linux
containers qualify their AlmaLinux userspace on the host kernel; AlmaLinux 10 AMD64
requires x86-64-v3. macOS 14.0 execution is not established by a deployment-target
marker. Developer ID signing, notarization and downloaded Gatekeeper launch are
untested. No Windows-native executable or macOS x86_64 package is provided.

Workgraph remains local and cooperative: actor identities, capabilities and
reservations are not authentication or physical file locks. The harness owns
process launch/termination, context/prompt policy, filesystem edits, external side
effects and provider spending. Cancellation, heartbeat state and lease expiry do
not prove a process stopped. There is no MCP/model runtime, distributed writer
coordination, automatic history pruning/compaction or garbage collector. Retained
output and selected provenance disclose their limits; correctness tests make no
scaling, model-performance or hardware power-loss claim.
