# v0.3 fresh-agent recovery comparison

On 2026-10-09, two fresh GPT-6.1 Sol agents using high reasoning recovered the same
small synthetic task through the live Codex agent harness. They received no earlier
agent transcript. One received Workgraph's entry guide, connection values and an
objective; the other received equivalent source notes in a Markdown directory.
Neither was given API method names, request shapes or recovery coaching. Each had
a limit of 20 observed read/list/CLI operations.

The fixture supplied an initial configuration proposal, a deliberately stale handoff,
a later correction, exact current settings, a historical verification record and
an outstanding clarification. Workgraph was gracefully restarted between the stale
handoff and the correction. The corresponding source text was checked against the
Markdown files before the agents began. Analysis was complete; implementation was
pending. The fixture's 14 passing parser cases were supplied historical evidence,
not tests executed by the recovering agents.

Both agents recovered namespace `ledger-current`, a 45-second refresh interval and
disabled bootstrap prefill. They identified `ledger-proposal` and 30 seconds as
superseded, cited the correction and current settings, and left implementation and
new verification pending. Neither claimed to have rerun the historical tests.

The Markdown agent saved and read back `answer.md`. The Workgraph agent discovered
resume, selected fact recovery, resource reads, request lookup, threaded replies
and request resolution. It saved exact retry requests, recorded an answer with
resource versions/digests and remaining work, and resolved the clarification.
The primary reviewer verified its answer against the fixture bytes, restarted the
daemon, and compared complete request/comment/ticket/fact readbacks: they were
unchanged at workspace revision 18. The ticket remained `todo` and unclaimed.
Both evaluation daemon lifetimes were stopped after verification.

## Separate delivery acknowledgement

The Workgraph agent **did not acknowledge request delivery**. Resolving a request
and acknowledging its delivery are separate operations. The original observer-side
postcheck expected acknowledgement and failed that assertion; the reviewer retained
that result, separately verified the successful answer/resolution, and did not
coach the agent or manufacture an acknowledgement afterward. Delivery remained
unacknowledged after restart.

The assigned objective required answering the clarification and retaining remaining
work; those actions succeeded. This is not evidence that an unfamiliar agent will
perform every communication housekeeping step without an explicit workflow rule.
If a harness requires delivery acknowledgement as well as resolution, its operating
instructions should state that requirement.

## Observed retrieval cost

A neutral local helper recorded document reads/listings and CLI invocation output,
including repeated reads, return codes and stdout/stderr byte counts. Setup and
reviewer verification were excluded. Markdown writes outside the helper were not
counted; these are retrieval/CLI operations, not all model tool calls.

| Observation | Markdown | Workgraph |
| --- | ---: | ---: |
| Recorded operations | 8 | 19 |
| Document/file reads | 7 | 7 |
| Directory listings | 1 | 0 |
| CLI calls to the daemon | 0 | 8 |
| Offline CLI help calls | 0 | 4 |
| Returned stdout bytes | 3,793 | 147,730 |
| Returned stderr bytes | 0 | 231 |
| Operations with nonzero exit status | 0 | 0 |

Workgraph document reads accounted for 123,458 stdout bytes, four brief help calls
for 8,141 bytes, and daemon calls for 16,131 bytes. The communication reference was
read twice. Mutation stderr contained saved-request notices. The observer emitted
whole files; outer tool output limits may further affect what reaches model context.
These counts therefore do not measure model context consumption.

For this small task, Workgraph retrieved substantially more material than Markdown.
Brief help was usable without full schemas, but broader reference-document reading
still dominated retrieval. The result supports successful discovery and durable
recovery, not a general efficiency or token-saving claim. Provider token usage was
unavailable and was not estimated from bytes.

## Limits

This was one controlled fresh-context reset, not an observed production compaction,
randomized benchmark, multiweek workload or comparison across different harnesses.
No productivity or general token-saving conclusion follows from one synthetic task.
The [earlier recovery exercise](agent-recovery.md) is historical context; differences
in tasks, prompts, methods and agent choices prevent a controlled before/after
performance claim. The source-tree binary was tested on macOS ARM64; this exercise
does not replace native installed-artifact qualification.
