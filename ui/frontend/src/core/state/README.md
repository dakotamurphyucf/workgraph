# Captured operations and progress

Create one `OperationController` in the application services, outside React view lifetimes. Register immutable preparation data and await admission, then call `act(intention, action)` only for an explicit user action. Subscribe to the same entry for pending state and observed results. A current actor, route or connection selection never replaces the captured writer or target. Upcoming ticket and comment forms should reuse this owner.

When an explicit prepare, execute, retry, recover or Inspect returns `sending`, the controller starts finite read-only inspection of that exact saved operation. Ordinary prepared-unsent results, adoption, listing and navigation never start observation. An explicit preparation recovery can observe an already-sending saved intention. It sends no further mutations, receipt recovery, acknowledgements or new request identities. Same-intention actions coalesce; a new explicit action supersedes only the background inspection read. Every result still passes the worker's full domain validation and the controller's identity, receipt and revision checks. An older or cancelled response cannot replace a newer result.

`ManagedOperation.observation` distinguishes active observation from completion, uncertainty, inspection failure, elapsed deadline, exhausted read budget, cancellation, disposal and capacity exhaustion. Retain the last observed operation and show these distinctions beside its explicit Inspect control. A remaining `sending` state after observation stops is not a completed action. Network, protocol and missing-operation failures stop observation; they never cause an automatic write retry. Unexpected exceptions retain their original identity for the error boundary.

`createProgressObserver` is the shared small lifecycle primitive for saved operations and local daemon-start plans. A start coalesces the same key without extending its deadline. It admits at most eight active identities, twelve inspections and thirty seconds per explicit start, including a stalled read. Backoff is 150, 300, 600, 1000, 1500 and then 2000 milliseconds. No permanent scan or polling of the saved-operation directory occurs. Deadline, stop and disposal abort only the inspection signal, never an admitted daemon write or launched process. Startup adapters must inspect the original saved plan and preserve its revision and endpoint identity; readiness does not establish process ownership.

The application launch disposes its observers before disposing protocol processing. A view unmount or writer switch does not dispose the shared owner. Explicit Inspect remains available after a finite observation ends, and can begin another bounded window if it still observes `sending`. Retry and receipt recovery are separate explicit choices.
